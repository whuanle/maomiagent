# Desktop Default Context Menu Guard Design

Date: 2026-06-07

## Goal

在桌面端主视图里默认禁用系统原生右键菜单，避免普通页面区域弹出浏览器默认菜单；同时保留已有和未来显式声明的自定义右键功能，例如文件标签、文件树节点、Git 分支树节点。

本设计采用“默认禁止，显式放行”的策略，不引入页面级开关，不做组件库级自动猜测。

## Problem Statement

当前主视图中的大多数区域仍会直接弹出系统原生右键菜单，例如返回、刷新、打印、检查等。这些菜单对桌面前端壳场景没有业务价值，也会破坏整体产品感受。

与此同时，系统里已经存在少量真正有业务含义的右键入口，例如文件相关节点和 Git 分支节点。这些入口不能因为全局禁用策略而失效。

问题的关键不是“是否支持右键”，而是“哪些区域被明确授权支持右键”。

## Confirmed Constraints

- 默认情况下，桌面端主视图中的系统原生右键菜单必须被禁用。
- 输入框、文本域、`contenteditable` 区域不做例外处理，仍按默认禁用。
- 已有自定义右键功能必须继续正常工作，尤其是文件标签、文件树、Git 分支树这类入口。
- 放行规则必须显式、可维护，不能依赖猜测某个节点是不是 Ant Design 组件或浏览器原生可编辑控件。
- 本轮只处理主视图渲染层，不改 Electron 或桌面宿主层的原生菜单策略。

## Non-Goals

- 不为普通页面区域新增自定义右键菜单。
- 不对整个页面、整个模块做大面积放开。
- 不引入“输入框允许右键、其它区域禁用”这类例外分支。
- 不依赖 CSS 或视觉隐藏方式掩盖系统右键。
- 不修改现有业务菜单项内容，只控制右键事件是否允许触发。

## Recommended Approach

推荐新增一个全局主视图右键守卫，在启动层统一监听 `contextmenu` 事件，并采用严格白名单放行：

1. 默认拦截所有 `contextmenu`
2. 仅当事件目标或祖先节点命中 `data-allow-context-menu` 时放行
3. 所有已有自定义右键触发节点显式补上该属性

这是本设计唯一推荐方案，因为它最符合“默认禁止，显式授权”的产品规则，也最容易长期维护。

## Architecture

### Guard entry point

新增一个渲染层工具，例如：

- `apps/desktop/MaomiAgent/src/mainview/lib/desktop-contextmenu-guard.ts`

导出 `installDesktopContextMenuGuard(document?)`，并在主视图启动入口 `main.tsx` 中安装，和现有缩放守卫、外链守卫保持同层级。

### Guard behavior

守卫在 `document` 上监听捕获阶段的 `contextmenu` 事件：

- 如果事件已被取消，直接返回
- 如果事件目标不是 `Element`，默认拦截
- 如果事件目标自身或任一祖先节点命中 `[data-allow-context-menu]`，直接放行
- 否则执行 `preventDefault()`

守卫只负责“是否阻止系统默认右键菜单”，不负责渲染业务菜单，也不关心菜单项内容。

### Whitelist contract

白名单约定只保留一个显式契约：

- `data-allow-context-menu`

任何需要触发自定义右键菜单的节点，都必须在事件触发容器或其明确父容器上带这个属性。

本轮不增加第二套备用规则，例如自动识别 `Dropdown trigger={["contextMenu"]}`、自动识别某类弹层、自动识别可编辑元素等。后续新增右键功能时，也必须遵守这个属性契约。

## Integration Scope

### Existing context menu entry points

本轮需要检查并补齐至少以下现有入口：

- 文件标签相关右键触发节点
- 工作区文件树节点右键触发节点
- Git 分支树节点右键触发节点

补标记时应加在真正触发 `contextmenu` 的容器上，而不是整页外层容器，避免把无关区域也一并放开。

### Future context menu entry points

后续如果新增任何业务右键能力，开发规范固定为：

1. 右键触发节点显式加 `data-allow-context-menu`
2. 再挂接对应的自定义菜单逻辑

如果只实现了菜单逻辑但没有加属性，则会被全局守卫拦截。这是预期行为，不算框架缺陷。

## Error Handling

- 全局守卫本身不得抛出异常影响页面渲染
- 如果事件目标解析失败，安全策略应退回默认拦截
- 某个业务区域遗漏白名单属性时，表现为“右键菜单不出现”，但不能影响左键、键盘和页面其它交互

## Testing

至少补充以下覆盖：

1. 默认普通节点触发 `contextmenu` 时会被拦截
2. 带 `data-allow-context-menu` 的节点触发 `contextmenu` 时不会被拦截
3. `input`、`textarea`、`contenteditable` 在未标记时仍会被拦截
4. 触发节点的子元素触发右键时，只要祖先带标记也会放行
5. 现有关键右键入口继续正常工作，至少覆盖文件相关入口和 Git 分支树入口

## Rollout Notes

- 这是一次主视图交互约束收口，不是新功能曝光
- 目标是去掉无意义的系统右键菜单，同时保住真正有业务价值的右键入口
- 以后排查右键问题时，先检查触发节点是否带 `data-allow-context-menu`

## Success Criteria

- 主视图中普通页面区域不再弹出系统原生右键菜单
- 输入类区域同样不会弹出系统原生右键菜单
- 文件标签、文件树、Git 分支树等已有业务右键入口仍然可用
- 新增右键功能时，团队只需遵守一个显式白名单属性即可接入
