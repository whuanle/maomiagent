# UI 设计师工作区查询服务设计

## 背景

`UI 设计师` 页面左侧“工作区与对话”下拉当前在 `use-ui-designer-shell-state.ts` 中直接调用 `listDesktopWorkspaces()`，并将返回结果原样写入页面状态。由于微信、飞书用户会自动生成外部渠道专属工作区，这些专属工作区也会进入 UI 设计师的工作区下拉，导致页面出现不该给普通设计流程使用的工作区。

当前主视图内已经存在“普通工作区选择器只显示普通工作区”的需求，但实现方式分散：

- `聊天` 页面会在加载后过滤外部渠道工作区。
- `Git`、`微信`、`飞书机器人配置` 页面也各自调用过滤函数。
- `UI 设计师` 页面尚未接入这条规则。

问题不只是 UI 设计师少了一次过滤，更在于“页面自己决定要不要过滤、怎么过滤”，工作区查询边界不清晰。

## 目标

- `UI 设计师` 工作区下拉只显示普通工作区，不显示微信、飞书外部渠道工作区。
- 在主视图层提供明确的工作区查询服务接口，区分“获取普通工作区”和“获取全部工作区”。
- 让 `UI 设计师`、`聊天`、`Git`、`微信`、`飞书机器人配置` 这类页面统一通过服务层取工作区，避免各页散落查询和过滤逻辑。
- 保持现有 bridge、共享类型和存储结构不变。

## 非目标

- 本次不修改 `DesktopWorkspaceItem` 结构，不新增 `workspaceType`、`scope` 等后端显式字段。
- 本次不调整工作区持久化、bridge 协议或数据库表结构。
- 本次不改变“外部渠道工作区仍然存在并可被特定流程使用”的产品能力；只规范普通页面的查询入口。

## 方案

在 `src/mainview/services/` 新增一个工作区查询服务，例如 `workspace-query-service.ts`，作为主视图页面访问工作区列表的统一入口。

服务职责限定为三件事：

1. 封装 `listDesktopWorkspaces()` 的调用。
2. 对“普通工作区”应用统一过滤规则。
3. 在需要时提供统一的 `Select options` 映射。

建议提供的接口如下：

- `getAllWorkspaces(query?)`
  - 直接返回 bridge 层原始工作区列表。
  - 供确实需要全量工作区的场景显式调用。
- `getNormalWorkspaces(query?)`
  - 内部调用 `getAllWorkspaces(query?)`。
  - 使用现有 `filterSelectableDesktopWorkspaces()` 过滤微信、飞书外部渠道工作区。
- `toWorkspaceOptions(items)`
  - 将 `DesktopWorkspaceItem[]` 映射为统一的 `{ label, value }` 列表。
  - 避免页面反复拼接 `name + workspaceId`。

## 查询规则

“普通工作区”的定义沿用现有前端过滤规则，不新增另一套判断：

1. `workspaceId` 以 `wechat-` 或 `feishu-` 开头的工作区，视为外部渠道专属工作区。
2. `directoryPath` 命中 `.../desktop/workspaces/channels/wechat/...` 或 `.../desktop/workspaces/channels/feishu/...` 的工作区，视为外部渠道专属工作区。
3. 其余工作区视为普通工作区。

这意味着本次服务层只是把既有过滤规则集中收口，不改变判定逻辑。

## 页面接入

### UI 设计师

- `use-ui-designer-shell-state.ts` 不再直接依赖 `listDesktopWorkspaces()`。
- 页面改为调用 `getNormalWorkspaces()`。
- 工作区状态、默认选中逻辑和空状态保持现有行为，只是数据源变成普通工作区列表。

### 聊天

- `use-chat-page-shell-state.ts` 改为通过 `getNormalWorkspaces()` 取列表。
- 页面不再自己调用 `listDesktopWorkspaces()` 后再过滤。

### Git

- `page.tsx` 改为通过服务层获取普通工作区列表并构建 options。

### 微信 / 飞书机器人配置

- 保持“切换范围只能选普通工作区”的行为不变。
- 页面改为通过工作区查询服务获取普通工作区或普通工作区 options，不再自行组合过滤逻辑。

## 错误处理

- 服务层不吞掉 bridge 查询错误，保持向页面抛出，让页面沿用现有错误提示与空状态行为。
- 过滤后没有普通工作区时，页面保持当前逻辑：
  - `UI 设计师` 继续显示未选中工作区/准备状态。
  - `聊天`、`Git`、`微信`、`飞书` 保持各自现有空状态或禁用行为。

## 测试

- 为工作区查询服务补单测：
  - `getAllWorkspaces()` 返回原始结果。
  - `getNormalWorkspaces()` 会过滤微信、飞书外部渠道工作区。
  - `toWorkspaceOptions()` 输出稳定的 `label/value` 结构。
- 为 `UI 设计师` 补回归测试，确认工作区下拉不再出现微信、飞书工作区。
- 已有依赖过滤行为的页面测试如需调整，统一改为断言服务层结果，而不是页面内私有过滤细节。

## 取舍说明

这次不直接把“工作区类型”做成共享显式字段，是因为那会把改动范围扩展到主进程模块、bridge 协议、共享类型和数据迁移，超出当前问题的必要范围。当前最重要的是把查询边界收口，让页面不再各自决定是否过滤工作区。

等后续需要更稳定的工作区分类能力时，再考虑把“普通工作区 / 微信工作区 / 飞书工作区”升级为后端显式模型字段；届时前端服务接口仍然可以保持不变，只替换内部判定来源。
